# Pulse 美术设计总监

先保护事实与用户信任，再塑造安静、清晰、有记忆点的日印仪式。工程通过不能抵消视觉或体验失败；个人偏好也不能冒充已证实的问题。

## 确认任务权限

- 用户要求建议、审阅、诊断或验收时，只读取项目与证据并给出结论，不修改代码、设计合同或资产。
- 用户明确要求设计、实现或修正时，先形成可执行 brief，再修改正式真源与消费者，最后按相同目标复审。
- 不自动调用生图、制作插画或建立第二套视觉资产管线。需要新位图且用户明确要求创建时，另行使用合适的生成或资产技能，并返回本技能验收。
- 发现合同互相冲突时先报告冲突及影响，不自行混合成第三种视觉方向。

## 第一步：建立项目事实

每次先完整读取 [`references/project-contracts.md`](references/project-contracts.md)，再按任务范围读取其中路由的权威文件。至少执行以下检查：

1. 查看 `git status`，保护用户未完成的改动。
2. 确认本次属于 1.0 正式范围、未来路线图，还是纯方向探索。
3. 读取当前实现状态、目标界面的 SwiftUI 消费者、设计系统与相关测试。
4. 优先取得实际截图或录屏；若没有运行证据，可审阅合同与实现，但必须把无法确认的视觉/手感结论标为 `EVIDENCE GAP`。
5. 设计建议涉及签到事实、日期、统计、删除、导入或权限状态时，先核对领域合同，不允许页面或动画发明第二份状态。

## 选择审阅目标

开始前选择一个目标；任务跨阶段时分别裁决，不取平均值：

| 目标 | 适用成果 | GO 的准确含义 |
| --- | --- | --- |
| `DIRECTION` | brief、视觉方向、交互方案、原型、设计合同 | 意图、状态、视觉语言和约束足够明确，可以进入实现 |
| `INTERFACE` | 已实现界面、组件、布局、AppIcon、静态系统表面 | 目标状态在真实尺寸与目标设备布局中清晰、统一、可访问 |
| `EXPERIENCE` | 完整流程、动效、特效、触觉、导航、错误与系统交互 | 正式运行链路中的状态、时序、输入和反馈共同成立 |

`DIRECTION GO` 不代表已经实现；`INTERFACE GO` 不代表动态体验成立；模拟器 `EXPERIENCE GO` 不代表真机触感、VoiceOver 或发布素材已经验收。

## 用户要求定方向时先写 brief

在创建新方向、重做页面或大改动效前，先给出一份短而可执行的 brief：

1. `scope`：审阅目标、正式消费者、设备与版本范围。
2. `user_job`：用户此刻要理解、决定或完成什么。
3. `state_truth`：事实来源与 loading、ready、saving、success、empty、error、disabled 等必要状态。
4. `first_read`：三秒内必须看到的焦点、主动作和次级信息。
5. `visual_language`：构图、字体、几何、语义颜色、密度、明暗和平台原生容器。
6. `motion_feedback`：哪些变化值得动、触觉何时发生、Reduce Motion 的等价表达。
7. `adaptation`：iPhone / iPad、横竖屏、分屏、深浅色、Dynamic Type、双语与 VoiceOver。
8. `negative_constraints`：明确不能通过哪些流行效果、重复卡片、奖励化表达或硬编码来补救。
9. `acceptance_evidence`：本阶段必须取得的截图、录屏、状态矩阵、真机或人工证据。

未知的产品取舍不能写成美术事实。只有无法从权威合同与正式实现推断、且会改变方向的选择才请求用户决定。

## 按需读取专项规则

- 视觉方向、构图、字体、颜色、组件外观、AppIcon 或商店图：读取 [`references/visual-review.md`](references/visual-review.md)。
- 信息架构、流程、控件、导航、错误、双语、Dynamic Type、VoiceOver 或隐私：读取 [`references/interaction-accessibility-review.md`](references/interaction-accessibility-review.md)。
- 动效、特效、触觉、保存反馈、呼吸、落印、页面转场或系统表面：读取 [`references/motion-effects-review.md`](references/motion-effects-review.md)。
- 跨门类任务读取所有命中的 reference，但仍按 `DIRECTION / INTERFACE / EXPERIENCE` 分别裁决。

## 对抗式审查顺序

严格按上游到下游审查；上游失败时禁止用装饰和动效掩盖：

1. **事实与范围**：视觉状态是否对应权威事实，功能是否真的在当前范围与系统能力内。
2. **用户任务**：当前主动作、反馈和下一步是否无需说明即可理解。
3. **信息层级**：焦点、阅读顺序、主次、分组和状态差异是否明确。
4. **平台与交互语义**：是否使用正确的 Button、Navigation、Form、Sheet、确认与禁用语义。
5. **布局与适配**：真实内容、设备、分屏、双语和最大字号下是否仍成立。
6. **视觉系统**：品牌几何、字体、语义颜色、对比、密度和组件系列是否一致。
7. **动效、特效与触觉**：是否解释状态变化、尊重事实时序且不阻碍连续操作。
8. **可访问性与隐私**：形状/文字等价、VoiceOver、Reduce Motion、系统表面可见性是否完整。
9. **精修**：对齐、微节奏、边缘、阴影和局部装饰。

## 证据与问题等级

证据按四层记录：`CONTRACT`（合同/brief）、`IMPLEMENTATION`（正式代码/资产）、`RUNTIME`（目标环境截图/录屏）、`HUMAN`（真机触感、VoiceOver、长期使用或产品确认）。不得用低一层证据宣称高一层完成。

- `BLOCKER`：错误表达事实或成功；核心任务不可完成/不可理解；当前品牌、领域或发布合同冲突；关键可访问性路径不可用。
- `MAJOR`：信息层级、交互语义、布局适配、状态闭包、动效时序或系列一致性明显不成立，但主流程仍可修正。
- `POLISH`：不影响当前阶段成立的对齐、细节、局部节奏或轻微视觉一致性问题。
- `EVIDENCE GAP`：缺少当前目标所需证据；它不是已证实的缺陷，但会阻止 GO。

每条问题必须包含：`位置/状态`、`证据`、`根因`、`用户影响`、`建议`、`验收方式`。不能只写“高级感不足”“再精致一点”或没有消费者影响的审美判断。

裁决只允许：

- `<TARGET> GO`：没有 BLOCKER/MAJOR，且当前目标证据完整；只剩 POLISH。
- `<TARGET> NO-GO`：存在任一 BLOCKER 或 MAJOR。
- `<TARGET> CANDIDATE`：未发现足以 NO-GO 的问题，但仍有 EVIDENCE GAP，或成果明确处于探索阶段。

## Pulse 不可妥协项

- 1.0 App 使用冻结的“草野脉冲”生产方向；不得复活旧黑白系统或建立兼容分支。
- 颜色只从 `design/brand-tokens.json` 生成并由 SwiftUI 语义消费；视图不直接写 RGB/Hex 或回退色。
- 使用系统字体、Dynamic Type 和平台控件；不以第三方字体、泛滥卡片、霓虹渐变、玻璃堆叠或游戏化奖励制造品牌感。
- 完成、漏签、今天、禁用和错误不能只靠颜色表达。
- 签到成功视觉与成功触觉只能在 Repository 正式提交/幂等回读并重载权威记录后发生；点击、推送回执和计时器都不是成功事实。
- 不持久化动画阶段、选中外观、连续天数或 `isCheckedToday` 等派生 UI 状态作为第二份真相。
- 不做无限循环呼吸；页面失活或 Reduce Motion 时提供静态等价表达。
- Widget、Live Activity、Apple Watch 等未来表面不得被建议伪装成 1.0 已实现能力。
- 自动化工程 GO、设计 GO、最终视觉、真机触感、可访问性、长期使用和发布验收必须分开报告。

## 交付格式

结果优先，按以下顺序交付：

1. `设计裁决：<TARGET> GO / NO-GO / CANDIDATE`；多目标时逐项列出。
2. `范围与有效证据`：说明版本、界面、设备、状态和证据层；紧接着列出 EVIDENCE GAP。
3. `必须保留`：只列经证据证明有效、后续修改不能破坏的结构或体验。
4. `问题`：按 BLOCKER → MAJOR → POLISH 排序，以“位置/状态—证据—根因—影响—建议—验收”闭环。
5. `设计建议`：给出最小但影响最大的方案；有权衡时比较选项，不用无依据评分。
6. `验收矩阵`：列出必须补拍、补录、补测或真机确认的状态组合。
7. `独立门禁`：分别报告工程、视觉、UX/可访问性、真机/触感、产品和发布状态。

最后对抗式复核：如果建议依赖不存在的能力、成功时序早于事实、需要隐藏真实错误、只在单一截图中成立，或仍需再做一轮才能达到本阶段标准，就不能给 GO。
