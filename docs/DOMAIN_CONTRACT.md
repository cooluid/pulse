# Pulse 签到业务规则

文档版本：1.0  
状态：Canonical Contract

本文档是日期和签到计算的唯一业务规则来源。实现、测试、界面文案和后续迁移必须遵循本文档。

## 1. 核心实体

### 1.1 签到项目 Habit

签到项目定义一组共享规则：

- 稳定的项目标识 `habitID`。
- 项目名称。
- 创建时间。
- 固定的签到时区 `timeZoneIdentifier`。
- 日界线偏移 `dayStartMinutes`，MVP 固定为 `0`。

MVP 只创建一个默认项目，但不得把唯一性建立在“数据库只有一个项目”这一偶然条件上。

### 1.2 签到记录 CheckInRecord

一条签到记录表示：

> 某个签到项目在某个逻辑日已经完成签到。

它至少保存：

- `habitID`：所属签到项目。
- `logicalDay`：业务日期，格式固定为 `yyyy-MM-dd`。
- `checkedAt`：用户实际完成签到的绝对时间。
- `createdAt`：记录写入时间。
- `source`：记录来源，MVP 为 `manual`。

## 2. 逻辑日

### 2.1 定义

逻辑日不是简单截取设备当前日期。计算输入包括：

- 当前绝对时间 `now`。
- 项目保存的 `timeZoneIdentifier`。
- 项目保存的 `dayStartMinutes`。

计算规则：

1. 使用 Gregorian Calendar。
2. Calendar 的时区设置为项目时区，而不是每次读取系统当前时区。
3. 从 `now` 减去 `dayStartMinutes`。
4. 取结果在该 Calendar 下的年、月、日。
5. 以固定公历格式生成 `yyyy-MM-dd`，不受用户语言和地区格式影响。

MVP 的 `dayStartMinutes = 0`，因此逻辑日从当地 00:00 开始。

### 2.2 时区固定规则

- 首次创建默认项目时，从系统时区初始化并持久化时区标识。
- 设备之后改变时区，不自动更改项目时区。
- 历史记录的 `logicalDay` 永远不因系统或项目时区变化而重写。
- P1 若允许修改项目时区，新时区只影响修改后的签到与日期展示边界。
- 修改时区前必须提示用户：短时间内跨时区可能导致当前看到的逻辑日改变。

固定时区的原因是避免旅行、系统设置变化或夏令时切换让同一个绝对时间被不稳定地归入不同业务日期。

### 2.3 夏令时

- 日期加减必须通过 `Calendar` 的日期运算完成，不得假定一天永远是 86,400 秒。
- 连续天数按逻辑日相邻关系计算，不按两个时间戳的秒数差计算。

## 3. 签到唯一性与幂等

唯一业务键：

```text
recordKey = habitID + ":" + logicalDay
```

规则：

- 同一个 `recordKey` 最多存在一条记录。
- 对已存在的 `recordKey` 再次执行签到，应返回现有记录，不新增记录。
- UI 禁用按钮只能改善体验，不能替代数据层唯一性。
- 签到操作必须在串行写入边界内完成“检查现有记录—插入—保存”。
- 持久化失败时，不产生成功状态，也不增加统计。

## 4. 签到与删除

### 4.1 创建签到

允许创建签到的条件：

- 目标项目存在且未归档。
- 目标逻辑日等于当前逻辑日。
- 数据库中不存在相同 `recordKey`，或操作按幂等规则返回现有记录。

MVP 不接受调用方传入任意历史日期，因此不能通过内部接口绕过 UI 实现补签。

### 4.2 删除签到

- 用户可以删除任意已有签到记录，以纠正误操作。
- 删除前必须明确显示目标日期并二次确认。
- 删除成功后，首页状态、月历和全部统计重新从记录计算。
- MVP 不保留删除审计记录，因为产品不承担考勤证明用途。
- 删除失败时保留原记录和原页面状态，并提示重试。

### 4.3 清除全部数据

- 清除范围包括默认项目、签到记录和应用内设置。
- 操作必须二次确认。
- 清除成功后重新创建一个空的默认签到项目，回到首次使用状态。
- 系统通知请求也必须一并取消。
- 如果任一关键删除步骤失败，不得显示“已全部清除”。

## 5. 日期分类

以项目创建逻辑日 `startDay`、当前逻辑日 `today` 和查询日期 `day` 判断：

| 条件 | 分类 | 是否计入完成率 |
| --- | --- | --- |
| `day < startDay` | 项目创建前 | 否 |
| `day > today` | 未来 | 否 |
| 存在签到记录 | 已签到 | 是，计为完成 |
| `startDay <= day < today` 且无记录 | 漏签 | 是，计为未完成 |
| `day == today` 且无记录 | 今日待签到 | 是，但不能在当天结束前称为“已漏签” |

## 6. 连续签到

### 6.1 当前连续天数

设 `today` 为当前逻辑日：

- 如果今天已签到，从今天开始向前逐日计算连续记录数。
- 如果今天未签到，从昨天开始向前逐日计算连续记录数。
- 今天尚未结束时，不因今天暂未签到提前把已有连续天数归零。
- 如果昨天也未签到，当前连续天数为 `0`。

示例：

| 记录情况 | 当前连续天数 |
| --- | --- |
| 周一、周二、周三已签到，今天是周三 | 3 |
| 周一、周二已签到，今天是周三且尚未签到 | 2 |
| 周一已签到，周二漏签，今天周三已签到 | 1 |
| 只有未来或项目创建前日期 | 0 |

### 6.2 最长连续天数

- 将所有有效 `logicalDay` 去重并按日期升序排列。
- 按 Gregorian Calendar 判断相邻逻辑日。
- 返回历史上最长的连续区间长度。
- 删除记录后重新计算，不保存可漂移的缓存值。

### 6.3 累计签到数

累计签到数是当前项目的有效签到记录数量。由于唯一业务键存在，它等于已签到逻辑日数量。

## 7. 月完成率

P1 若展示月完成率，定义为：

```text
本月已签到的有效日期数 / 本月应签到的有效日期数
```

分母只包含：

- 不早于项目创建逻辑日的日期。
- 不晚于当前逻辑日的日期。
- 位于所选月份内的日期。

未来日期和项目创建前日期不得进入分母。

## 8. 跨日刷新

应用必须在以下事件重新计算 `today`：

- App 启动。
- Scene 进入 active。
- 系统时钟或时区变化通知到达。
- 前台定时器检测到下一个逻辑日边界。
- 用户修改项目时区或日界线。

跨日刷新应更新今日状态和派生统计，但不得修改历史记录。

## 9. 可测试时间源

业务逻辑不得在计算深处直接调用 `Date.now`。时间必须通过可注入的 `Clock` 提供，以便测试：

- 零点前后。
- 月末和年末。
- 闰年 2 月 29 日。
- 夏令时开始和结束。
- 时区变化。

## 10. 数据导入与恢复

- Pulse JSON 使用显式 `schemaVersion`，当前版本为 `1`。
- 导入采用“验证完成后全量替换”语义，不做无法解释的自动合并。
- 替换前必须验证 schema 版本、项目时区、日界线、记录日期、记录来源、记录 ID 和逻辑日唯一性。
- 任一校验失败时，不得修改现有项目或签到记录。
- 导入前必须向用户显示记录数量，并明确告知现有签到数据会被替换且无法撤销。
- 持久化替换失败时必须回滚 `ModelContext`，现有内存状态继续对应数据库事实。
- 导入恢复签到项目和签到记录，不覆盖设备上的提醒时间、触觉和每周起始日偏好；导入完成后按新记录重新协调提醒。

## 11. 规则变更约束

以下需求都属于业务规则升级，不能只改界面：

- 补签。
- 多项目。
- 非零日界线。
- 多设备同步。
- 服务端防作弊。
- 删除审计。

加入其中任一能力前，应先更新本文档、迁移策略和测试矩阵。
